# CoreCRM – E2E Automation Suite

CoreCRM is a [Playwright Test](https://playwright.dev) end-to-end QA automation
portfolio project built with JavaScript and the Page Object Model (POM)
pattern. It automates and validates workflows in the
[Horilla CRM Demo](https://crm.demo.horilla.com) — the existing public demo
application under test (AUT) which CoreCRM tests but does not develop.

## Coverage

| Area | What is verified |
|---|---|
| Authentication | Login with valid credentials; rejection of invalid credentials |
| Leads | Creating a lead through the New Lead form, then **independently verifying persistence**: searching the leads list by the unique email, opening the matched record's detail page, and asserting it shows the persisted email and lead source |
| Contacts | Creating a contact through the New Contact form, then **independently verifying persistence**: searching the contacts list by the unique email, opening the matched record's detail page, and asserting it shows the persisted email and contact title |
| Accounts | Creating an account through the New Account form (unique name, required owner and industry), then **independently verifying persistence**: searching the accounts list by the unique name, opening the matched record's detail page, and asserting it shows the account name and the persisted industry; plus required-field validation on the empty Account Name |
| Opportunities | Creating an opportunity through the New Opportunity form (unique name, required stage and owner, amount, close date, and an associated Account selected from the live dropdown), then **independently verifying persistence**: searching the opportunities list by the unique name, opening the matched record's detail page, and asserting it shows the name, the persisted amount, close date, stage, and the associated account; plus required-field validation on the empty Opportunity Name |
| Activities | Creating a Task-type activity through the Create Activity form (unique subject) with a **Lead association selected through the real Select2 search widget**, then **independently verifying persistence**: searching the activities list by the unique subject and asserting exactly one row whose Related To cell shows the selected lead (the list row is the module's authoritative persisted view of the association — the detail page does not display it), opening the matched record's detail page via its `hx-get` URL, and asserting it shows the subject, activity type, and default status; plus required-field validation on the empty Subject |
| Campaigns | Creating a campaign through the Create Campaign form (unique name, required owner and Type, expected revenue, budget cost, pre-filled status default), then **independently verifying persistence**: searching the campaigns list by the unique name, asserting exactly one row that shows the type, owner, the pre-filled *Planned* status and the rendered amounts (`INR 2,500.00` / `INR 1,000.00`), opening the matched record's detail page via its `hx-get` URL, and asserting the header card shows the name, owner, type and rendered expected revenue; plus required-field validation on the empty Campaign Name |
| Lead Conversion | Converting a uniquely created lead through the lead detail page's Convert control in the demo's verified "Lead Conversion" modal: the form's pre-filled field mapping is asserted (Account Name ← lead company, Contact First/Last Name ← lead names, Opportunity Name ← `<lead company> - Opportunity`), then the conversion is submitted and independently verified: the success panel links the three created records, the created **Account** detail shows the company name plus the mapped Account Source (*Website*) and Industry (*Finance*), the created **Contact** detail shows the lead's unique email, the created **Opportunity** detail shows its name and links the created account in its Details tab, and the lead's converted state is verified — it disappears from the default leads list search and appears, as the exact same record, in the leads list's "Converted Lead" view |

## Test design

- **Authenticates once per run.** A `setup` project logs in and saves the
  session as Playwright `storageState` (`playwright/.auth/user.json`,
  git-ignored and never committed). The workflow tests reuse that session;
  the login tests always run unauthenticated. The file is regenerated by the
  setup project on every run, so it never needs to be part of a handoff.
- **Serialized on purpose.** The application under test is a shared public
  demo instance, so tests run one at a time (`workers: 1`, `fullyParallel:
  false`) to avoid simultaneous sessions colliding and to reduce load on the
  demo.
- **No fixed sleeps.** Tests rely on Playwright auto-waiting, web-first
  assertions, and screenshots/traces on failure.
- **Persistence is verified through the app's own list search.** After
  creating a record, the test navigates to the module list with the app's
  verified `search` query parameter (the same URL the in-app search action
  produces), asserts exactly one matching row, opens the matched record's
  detail page, and checks the persisted detail fields. Unique test emails
  (or unique account/opportunity names — accounts and opportunities have no
  identity email) make one row match.
- **Unique test data.** Every run creates records with `example.com` emails,
  unique `Aurora Systems <timestamp>.<n>` account names, unique
  `Aurora Opportunity <timestamp>.<n>` opportunity names, unique
  `Aurora Activity <timestamp>.<n>` subjects, unique
  `Aurora Campaign <timestamp>.<n>` campaign names, and unique
  `Aurora Convert <timestamp>.<n>` conversion leads (one helper builds the
  whole conversion data set so the four resulting records stay consistent),
  generated in `utils/test-data.js` — no real personal data. Test-created
  fictional records persist in the shared demo and are never deleted.
- **Credentials are never committed.** They come from `CRM_USERNAME` /
  `CRM_PASSWORD` environment variables (or a local `.env`, see `.env.example`).

## Prerequisites

- Node.js 20+
- Chromium for Playwright (`npx playwright install chromium`)

## Setup

```powershell
npm install
npx playwright install chromium
Copy-Item .env.example .env   # (PowerShell) then fill in CRM_USERNAME / CRM_PASSWORD
```

On macOS/Linux or Git Bash, use `cp .env.example .env` instead of `Copy-Item`.

To run against a different environment, override `BASE_URL`.

## Running the tests

| Command | What it does |
|---|---|
| `npm test` | All tests, headless |
| `npm run test:headed` | All tests with a visible browser |
| `npm run test:chromium` | Chromium projects only |
| `npm run test:debug` | Playwright inspector |
| `npm run report` | Open the HTML report of the last run |

A single file can be run with `npx playwright test tests/leads.spec.js`.

## Known demo limitations

- The demo site is shared and public; data created by tests is visible to
  everyone and resets periodically. Tests only create records — and run
  serialized for the same reason — they never edit or delete anything.
- **Temporary demo regression: list-row clicks are blocked.** The demo's
  lists were converted to HTMX partial navigation, and a transparent
  full-table `#loading-indicator` overlay now intercepts every pointer
  event over the rows — a real user cannot click a row either (verified live
  on 2026-11-04, affects all list modules). Mentor-approved temporary
  workaround: the tests extract the exact detail URL the matched row's name
  cell carries in its `hx-get` attribute (never constructed), assert it
  matches the module's detail-route pattern, and navigate to it directly.
  The original click methods are kept in the page objects, marked as
  currently unusable, so they can be restored when the demo removes the
  overlay.
- Leads, Contacts, Accounts, Opportunities and Campaigns persistence is
  verified independently of the create flow: after creating a record, the
  test searches the module's list view for the record's unique value (its
  unique email for Leads and Contacts; its unique name for Accounts,
  Opportunities and Campaigns), asserts exactly one matching row, opens the
  matched record's detail page through the verified URL above, and asserts
  on the detail page that the key values survived the save (email plus Lead
  Source for leads, email plus Title for contacts, name plus Industry for
  accounts, name plus amount/close date/stage/Account association for
  opportunities, name plus owner/type/rendered expected revenue for
  campaigns). Activities persistence is verified through the list row
  instead (its detail page does not display the Related To association).
- The Parent Account relationship in the Accounts form is **deferred**: the
  dropdown exists, but the demo does not persist the selection (verified
  live during Phase 2B.2; see `PHASE_2B_2_REPORT.md`). No fake coverage was
  added.
- On Opportunities only the verified behaviors are covered: the create form,
  the required Opportunity Name, the persisted amount (rendered with the
  demo's currency formatting), close date, stage and Account association.
  Stage pipeline progression, Probability auto-derivation, Primary Campaign
  Source, Link Leads, Duplicate and Change Owner are not verified and not
  covered (see `PHASE_2B_3_DISCOVERY.md`).
- On Campaigns only the verified behaviors are covered: the create form, the
  required Campaign Name / Campaign Owner / Type, the pre-filled *Planned*
  status default and the rendered Expected Revenue/Budget amounts. **The
  Lead ↔ Campaign association is deferred**: the Create Campaign form has no
  lead selector and the detail page only shows read-only aggregate counts
  ("Leads in Campaign" etc.), so the relationship cannot be verified from
  the Campaigns side without modifying Lead records (verified and documented
  in `PHASE_2B_5_DISCOVERY.md` §5). Parent Campaign is deferred like the
  Accounts module's Parent Account; Save & New, Import, Filters, other
  views, date persistence and status editing are not verified and not
  covered.
- On Lead Conversion only the verified default path is covered: converting a
  lead with all three entities in their rendered default "Create New" mode.
  The conversion form offers only Create New or Select Existing for
  Account/Contact/Opportunity — there is **no skip option** — and no
  client-side required fields, so no negative test was automated (no stable
  validation scenario exists). The **select-existing branches** (existing
  Account/Contact/Opportunity lookups; the existing-opportunity lookup is
  account-scoped and disabled until an account is chosen) are documented but
  not covered, to avoid doubling persistent conversion data for the same
  business assertion (see `PHASE_2B_6_DISCOVERY.md` §2, §9).
- **The account-side related-list relationship assertions are deferred
  (demo-blocked).** The opportunity's Details tab authoritatively shows the
  created account link, but the account detail page's Related Lists side
  lists — the only surface listing the created contact/opportunity on the
  account side — sit under a permanently rendered, invisible
  `#tab-related-lists-indicator` overlay that intercepts every pointer
  event over their anchors (real-user clicks included; verified live on
  2026-11-04). The anchors have no keyboard binding and their content
  routes are htmx-only (405 on direct navigation), so the browser-driven
  assertion is deferred; no force-click or workaround was introduced (see
  `PHASE_2B_6_DISCOVERY.md` §6).
- Detail pages do not always open on the "Details" tab: the demo persists
  the last active detail tab per user (server-side `saveActiveTab`),
  so the tests explicitly click the Details tab before any tab-scoped
  assertion.
- **Lead conversion creates 4 persistent records per run**: 1 lead
  (created through the leads UI) plus, from its conversion, 1 account,
  1 contact and 1 opportunity, all fictional and timestamp-unique — the
  converted lead additionally moves out of the default leads list into the
  "Converted Lead" view. Records are never deleted.
- Activities are covered where the demo's behavior could be verified
  end-to-end: Task-type activities only (the module's tab-default type), a
  Lead association selected through the real Select2 search widget, and the
  persisted association asserted on the **activities list row**, which is
  the module's authoritative persisted view of the relationship — the
  activity detail page does **not** visibly display the Related To record
  (verified live on 2026-11-04; see `PHASE_2B_4_DISCOVERY.md`). Meetings/
  Calls/Events flows, multi-assignee/participant fields, reminders,
  start/end datetimes, priority and status editing are not verified and not
  covered.
- Saving an activity behaves differently from the other modules: the demo
  shows "Activity created successfully." and **stays on the activities
  list** — there is no detail-page redirect.
- The Related To options are not pre-rendered: the control is a remote
  Select2 (`select2-pagination`) that loads matching records from the
  server only when the widget is opened and searched. Picking an Activity
  Type or Related Content Type also re-renders the whole create form
  asynchronously through HTMX; the tests wait for that re-render to
  actually swap the form before interacting further.
- The success confirmation is a SweetAlert2 dialog that closes
  automatically after a few seconds. The tests assert its appearance, then
  independently verify record persistence through the module's list search
  and record detail page.
- The demo is Chromium-validated only; Firefox/WebKit are documented as an
  opt-in, later step in `playwright.config.js`.
